# Database migrations and explicit adoption

## Safety and current readiness

**V1 adoption is complete for local PostgreSQL, the isolated Neon rehearsal, and
Neon production.** The corrected production backend passed Spring Boot, Flyway,
and Hibernate startup validation; the operator subsequently confirmed that the
live website's core functionality works. See the
[completed milestone and evidence boundaries](flyway-production-adoption-report.md),
[deployment checkpoint](neon-production-backend-release-checkpoint.md), and
[recovery checklist](neon-production-recovery-checklist.md).

For an already-adopted database, use `database.ps1 -Command validate` with its
existing secure configuration. **Do not repeat reconciliation or baseline.**
The adoption procedures below apply only to a separately reviewed database with
no migration history. The drift table records the original local audit; those
differences were resolved. See [local reconciliation](local-schema-reconciliation.md)
and [the shared CLI/startup validation fix](flyway-baseline-validation-fix.md).

Spring Boot **4.0.6** manages **Flyway 11.14.1**. The backend uses
`spring-boot-starter-flyway` (Boot 4's Flyway auto-configuration module) and
`flyway-database-postgresql`. Hibernate only validates. No entity, financial
calculation, JWT, market provider, notification rule, or frontend change is required.

**Do not deploy this backend onto an unadopted populated database.** Startup
intentionally fails until migration history is established. Adoption was completed
in separate approved operator stages after implementation and recovery testing.

Read-only inspection of local PostgreSQL **17.9** found nine tables, eight
`GENERATED BY DEFAULT AS IDENTITY` bigint sequences, seven user foreign keys,
four named unique constraints and ten application indexes. Snapshot prices use
`numeric(36,12)`, other financial amounts `numeric(19,4)`, and shares
`numeric(19,6)`. Java `LocalDateTime` is `timestamp(6) without time zone`; `Instant`
is `timestamp(6) with time zone`. Enum values use varchar plus CHECK constraints.
Timestamps/booleans have Java lifecycle defaults, not SQL defaults. Notification
tables cascade on user deletion; other user foreign keys do not. Legacy
`ai_insights` remains mapped even though deterministic insights are dynamic.
No application-defined functions, triggers, views or extra extensions appeared in
the schema export. Internal FK triggers and the standard `plpgsql` extension are expected.

### Local differences that block adoption

The canonical V1 reflects **current entity mappings**, not silently tolerated drift:

| Object | Existing local schema | Canonical V1 |
| --- | --- | --- |
| `budgets_category_check` | Excludes `FOOD`, `RENT`, `HEALTH` | All 19 `TransactionCategory` values |
| `transactions_category_check` | Excludes `FOOD`, `RENT`, `HEALTH` | All 19 values |
| `ck_investments_shares_positive` | Missing | `shares > 0` |
| `ck_investments_purchase_price_positive` | Missing | `purchase_price > 0` |

Hibernate's `update` did not synchronize those existing checks. Its `validate`
does not check all constraints/indexes, so Hibernate validation alone is insufficient
evidence for adoption. Do not change data, disable checks, edit the manifest, or use
`repair` to make verification pass. Request separately reviewed reconciliation
after checking investment values read-only. Expanding the category checks does
not require changing records; adding positive investment checks still needs data
validation and explicit approval. No reconciliation SQL is automatically executed
or shipped in a migration. Until resolved and reverified, the actual local database
**must not be baselined**. Neon was not contacted and may have different drift.

## Migration ownership and startup modes

`src/main/resources/db/migration/V1__initial_schema.sql` creates all nine application
tables, eight identity generators, PKs, FKs, uniques, enum/value checks and indexes
on an **empty** `public` schema. It contains no financial inserts or reconciliation.
Flyway history records V1's checksum. Existing verified databases are explicitly
baselined at **1**, which records a BASELINE row and **does not execute V1**.
Subsequent changes start at V2.

Settings: Flyway enabled; `ddl-auto=validate`; SQL initializer disabled;
`baseline-on-migrate=false`; `clean-disabled=true`; schemas/default-schema `public`;
schema creation disabled; checksums and file names validated; out-of-order disabled;
no future/missing migration ignore patterns. Unsupported baseline versions fail.
Attempts to override Hibernate back to `update`/`create`, automatic baselining or
clean fail at startup. `DB_DDL_AUTO` is obsolete; remove it from deployment settings.

* Default / production `DB_MIGRATION_MODE=validate`: check existing history and
  checksums, reject missing/pending/unknown migrations, then Hibernate validates.
  No startup migrate/baseline/history creation. Use a runtime DB role without DDL
  permissions once permissions have been reviewed independently.

  CLI `validate` and this startup mode share `DatabaseMigrationTool.validateHistory`.
  V1 `BASELINE_IGNORED` is accepted only with genuine successful BASELINE 1 history
  and matching Flyway info. Other unapplied/ignored/failed/unexpected states are
  rejected even if Flyway validation itself succeeds.
* Local `start-dev.ps1`: defaults to `migrate` only if the environment has no value;
  refuses nonlocal URLs. Flyway can initialize an empty schema and apply future
  migrations to an adopted schema. An unbaselined nonempty schema fails without
  creating history. Set `DB_MIGRATION_MODE=validate` to prohibit startup migrations.
* Tests: Surefire activates `test`; connections use `TEST_DB_*`, not `DB_*`.
  A context initializer rejects remote/non-test URLs, port 5432, and URL overrides.
  `run-tests.ps1` starts a new isolated cluster/database, disables real AI/market
  credentials and schedulers, runs the suite, then stops only its own cluster.
  Existing provider tests use mocks or local HTTP fixtures.

Flyway initialization precedes JPA through Boot's database-initializer dependency
ordering. Do not set `spring.flyway.enabled=false` to bypass adoption.

## Tools

From the repository root:

```powershell
cd backend/backend
.\run-tests.ps1
# Optional: .\run-tests.ps1 -Tests FlywayMigrationTests
# Optional custom installation: -PostgresBin 'C:\Program Files\PostgreSQL\17\bin'
```

Docker Desktop is installed here but its daemon is unavailable, so the test runner
uses installed PostgreSQL tools instead of making the suite Docker-dependent.
Its cluster is loopback-only with trust authentication, a random unused port and
unique `ft_test_` database. Stopped data/logs remain under ignored `.local/` for
diagnosis; they contain synthetic test records, not real finances. Never point
tests at an existing database. Direct `mvnw test` without a disposable connection
fails safely for integration tests; unit-only filtering still works without PostgreSQL.

`database.ps1` builds the packaged backend then invokes a standalone migration
main class through Boot's `PropertiesLauncher`. It **does not start Spring**, a
scheduler, financial services or external providers. Local DB password loading is
shared with `start-dev.ps1` using Windows user-encrypted storage. Explicit environment
values take precedence; original variables are restored. Migration commands do not
create or require a JWT secret. No credentials go in command arguments or source files.

Commands: `verify` (read-only strict V1 schema check), `validate` (read-only migration
history/checksum check), `baseline` (explicit history write), `migrate` (explicit DDL).
Remote use requires `-AllowRemote` and explicit database credentials. That switch
is an operator acknowledgement, not permission to change production during this task.

The verifier compares a committed V1 catalog manifest with actual PostgreSQL:
column types/precision/nullability/collation/defaults/identity; PK/FK/unique/CHECK
definitions including actions/validation/deferrability; index definitions and
validity; sequence definitions/ownership (not counters); relations/RLS; policies;
functions; noninternal triggers; enum/domain types; rules and installed extensions.
Unknown/missing/changed signatures reject adoption. It ignores physical column order,
owners, grants and sequence current values. Those permissions and objects outside
`public` require manual inspection. It is intentionally conservative about custom
constraint/index names and extension/version differences; review any mismatch.
The manifest is an adoption artifact for V1, not a mutable current-schema description.

## Local adoption: manual only, for databases without migration history

1. Stop backend writers/cron and DDL activity. Confirm the completed local backup
   is readable and test restoration into a separate disposable database. Preserve
   the schema export and backup timestamp. Do not assume a file's existence proves recovery.
2. Review/reconcile the four reported local constraint differences through a
   **separately approved** change; recheck existing financial data first. Do not
   baseline before verification succeeds. Use the separately reviewable scripts
   and commands in [the reconciliation guide](local-schema-reconciliation.md);
   they are outside the automatic Flyway migration path.
3. Configure/confirm the intended local target. Existing encrypted password loading
   still works; do not paste passwords into shell history:

   ```powershell
   Set-Location '<repository-root>/backend/backend'
   $env:DB_URL = '<configured local JDBC URL>'
   $env:DB_USERNAME = 'postgres'
   .\database.ps1 -Command verify
   ```

   With the original unreconciled schema this command **fails with the four
   differences** and makes no changes. Reconcile and reverify before first adoption.
4. Only after a successful verify, backup verification and explicit approval:

   ```powershell
   .\database.ps1 -Command baseline -ConfirmDatabase finance_tracker_db -BackupVerified
   .\database.ps1 -Command validate
   .\database.ps1 -Command migrate
   .\start-dev.ps1
   ```

   Baseline requires exact current database-name confirmation, locks the nine
   application tables exclusively, rechecks schema compatibility, then creates
   history through Flyway. Existing records/identifiers and sequence counters are
   untouched. Use a maintenance window; concurrent operators/DDL must be stopped.
5. Inspect `public.flyway_schema_history`: version 1, type BASELINE, success true;
   no V1 SQL row. Subsequent migrations record their SQL checksums. Compare record
   counts/identifiers, verify registration/login and core screens, restart and
   confirm no migration repeats. Do not delete or manually rewrite history.

For a genuinely fresh approved local database, use `database.ps1 -Command migrate`
or `start-dev.ps1`; V1 creates schema and a SQL history row automatically. No
baseline is needed. The database itself must already exist.

## Neon / Vercel adoption and deployment

The repository's `vercel.json` routes API traffic to a Java 21 container built by
`Dockerfile.vercel`; Next.js is a separate service. Containers may initialize
concurrently/repeatedly. Keep production `DB_MIGRATION_MODE=validate` and run
migrations once in a controlled maintenance/release job **before** compatible
backend deployment. Flyway uses PostgreSQL locking for migrations; this is not a
substitute for maintenance/deployment ordering or application compatibility.

1. Obtain explicit production approval and verify a usable Neon recovery point,
   retention/window and restore capability for the correct project/branch. Test
   restoration/branch creation. Neither backup nor production schema was verified here.
2. With approval, use a read-only role and Neon's **direct** connection endpoint
   for schema/catalog inspection, not application traffic. Inspect all custom
   schemas, functions, triggers, extensions and privileges. Run tool `verify` with
   `-AllowRemote`; it must pass before adoption. Investigate every difference.
3. Rehearse on an isolated Neon development branch with equivalent PostgreSQL
   version/extensions: fresh initialization, populated-copy verified baseline,
   Hibernate validate, restart, authenticated CRUD and history inspection. Providers
   and cron remain disabled during rehearsal; no market/AI credits are needed.
4. Stop production writers/cron and duplicate deployment starts. Use a controlled
   migration identity with DDL rights, secure env `DB_URL/DB_USERNAME/DB_PASSWORD`
   and direct JDBC URL with TLS. Never print URLs/credentials. Independently confirm
   target branch/database and verified backup, then:

   ```powershell
   .\database.ps1 -Command verify -AllowRemote
   .\database.ps1 -Command baseline -AllowRemote -ConfirmDatabase '<actual_database_name>' -BackupVerified
   .\database.ps1 -Command migrate -AllowRemote
   .\database.ps1 -Command validate -AllowRemote
   ```

   These are manual approved commands, **not** part of Vercel image build/startup.
   On Linux use the packaged Java command documented in `database.ps1`, passing
   arguments `verify`, `baseline <name> backup-verified`, `migrate`, `validate`.
5. Configure Vercel runtime with the pooled Neon URL and runtime identity,
   `DB_MIGRATION_MODE=validate`, unchanged JWT/CORS/provider secrets. Remove obsolete
   `DB_DDL_AUTO=update` and conflicting Spring schema overrides. Preview deployments
   must use a separate Neon branch, never an unadopted production database.
6. Deploy the compatible backend. Confirm startup checksum and Hibernate validation,
   history, authentication/ownership, CRUD, notification deduplication, analytics and
   quote snapshots. Re-enable approved cron only after smoke checks succeed.

If migration fails, stop deployment and inspect history/transaction state. PostgreSQL
transactional DDL usually rolls back a failing migration, but nontransactional operations
or partial external effects need specific recovery. Flyway Community does **not** supply
automatic down-migrations/undo. Do not clean/repair/edit applied scripts to hide failures.
Rolling back application code does not restore database state and can be unsafe if
old Hibernate update settings reappear. Prefer an approved forward fix; if restoration
is necessary, restore to a new Neon branch/target, validate it, switch connections in
a controlled outage, and account for writes since the recovery point.

## Future migrations

Create one sequential immutable `V2__description.sql`, then V3, etc. Update entity
mappings together with the migration, run the full disposable PostgreSQL suite and
rehearse on a populated clone. Keep changes compatible with deployment ordering;
use separate expand/backfill/contract stages for risky changes. Do not edit V1 or
its manifest after adoption, use `IF NOT EXISTS` to conceal drift, or change checksums
via repair. Review destructive SQL separately. Deploy DDL through the controlled
job, then the compatible application. Keep production validation-only.
